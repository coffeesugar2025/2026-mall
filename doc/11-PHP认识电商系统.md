## 一、 业务架构 (Business Architecture)
核心目标：弄清系统在商业上怎么跑通的，钱和货怎么流转。
## 1. 核心模式与用户

* 系统的核心商业模式是什么（如 B2C、B2B、B2B2C 还是多商户跨境电商）？
* 系统有哪些核心业务角色（如平台管理员、普通买家、商家、运营、财务、客服、物流人员）？
* 支持哪些注册与登录方式（如手机号、邮箱、微信/支付宝三方快捷登录、老系统的用户名）？
* 是否有完整的会员等级（VIP）体系及对应的成长值、经验值计算规则？
* 系统是否支持国际化（多语言、多货币、多时区展示）？
* 系统的日常日活（DAU）和月活（MAU）规模大概是多少？

## 2. 商品与库存业务

* 商品是单规格（SPU）还是多属性多规格（SKU）设计？
* 商品类目最多支持几级分类？
* 商品价格体系是怎样的（包含市场价、销售价、会员价、分销价、阶梯价吗）？
* 库存的扣减时机是什么（是下单扣库存、支付扣库存，还是预扣留+超时释放）？
* 系统如何处理商品虚仓、独占库存或区域库存（分仓）业务？
* 是否存在组合商品、加价购、附赠品等复合商品销售模式？

## 3. 促销与营销工具

* 系统支持哪些优惠券类型（满减券、折扣券、免邮券、品类券、店铺券等）？
* 优惠券的叠加规则是什么（能否与店铺满减、单品折扣同时使用）？
* 系统自带哪些营销玩法（如限时秒杀、拼团、砍价、积分商城、分销返利）？
* 促销活动的生命周期是怎样的（如何控制定时上架、预热和结束）？
* 积分的来源（消费、签到、评价）与消耗（抵现、兑换）逻辑是怎样的？
* 系统是否有导购或分销员（分销裂变）业务？

## 4. 订单与支付流程

* 从下单到完成，标准的订单状态机（状态流转图）是怎样的？
* 系统支持哪些支付渠道（支付宝、微信支付、银联、货到付款、余额支付等）？
* 多个商户的商品一起下单时，系统如何进行拆单（按商家、按仓库、还是按配送方式）？
* 订单超时未支付的自动取消时间是多少分钟？由什么触发？
* 是否支持合并支付、分期支付或定金+尾款（预售）模式？
* 订单的退款退货（逆向流程）怎么走（商家审核、拒签、部分退款、全额退款、运费险退理赔）？

## 5. 物流、履约与结算

* 系统如何计算运费（按件数、按重量、体积，还是按地区设置运费模板）？
* 物流信息的对接方式是什么（对接了快递100、鸟箱，还是人工维护物流单号）？
* 系统是否支持自提点、同城配送或前置仓业务？
* 商户/供应商的结算周期（账期）是怎样的（如 T+1、T+7、月结）？
* 平台的佣金/扣点扣除比例是如何配置和计算的？
* 财务对账的流程是怎样的（如何导出报表，如何处理微信/支付宝的账单不一致问题）？

## 二、 技术架构 (Technical Architecture)
核心目标：明确系统底层用了哪些技术栈，整体结构是什么样。
## 1. PHP 基础与框架

* PHP 5.6 的具体小版本号是多少（如 5.6.40）？
* 系统使用的是开源框架（如 ThinkPHP 3.2、Laravel 5.1、Yii 2.0、CI 3.x）还是纯原生/自研框架？
* 如果是开源框架，代码是否被前人深度魔改过？
* PHP 的运行模式是什么（Apache 的 mod_php，还是 Nginx + PHP-FPM）？
* PHP-FPM 的配置参数（如 max_children, start_servers, max_requests）是如何优化的？
* 系统中是否开启了垃圾回收（GC）机制，是否有配置 memory_limit？

## 2. 数据库与存储技术

* MySQL 数据库的具体版本是多少（PHP5.6 时代多为 MySQL 5.5 或 5.6）？
* 数据库的存储引擎是什么（MyISAM 还是 InnoDB，是否存在混用）？
* 是否使用了 Redis 或 Memcached 作为缓存？
* 如果是 Redis，主要用于哪些业务场景（缓存、Session 存储、分布式锁、队列）？
* 是否引入了全文检索技术（如 Elasticsearch、Sphinx、Coreseek）来支持商品搜索？
* 系统里的图片、视频等静态资源是存在本地服务器，还是用了第三方对象存储（如阿里云 OSS、腾讯云 COS）？

## 3. 消息队列与异步处理

* 系统是否存在异步处理机制？
* 使用了什么作为消息队列的中间件（Redis List/Zset、RabbitMQ、ActiveMQ，还是基于 MySQL 模拟的队列）？
* 系统中的定时任务（Crontab）是如何配置的？
* 定时任务是否有并发冲突的控制（防止上一次任务没执行完，下一次又启动）？
* 是否存在常驻内存的 PHP 守护进程（Supervisor 挂载的 PHP 脚本）？
* 如何监控异步队列的堆积情况和消费失败情况？

## 4. 高并发与扩展技术

* 系统架构是单体架构，还是已经做了服务拆分（如伪 SOA、早期微服务）？
* 数据库是否做了读写分离、主从复制，还是完全单机？
* 数据库是否做了分库分表？若有，分表键（Sharding Key）是什么？
* 前端是否配置了 CDN 加速？加速了哪些资源？
* 系统是否使用了反向代理（如 Nginx、HAProxy）进行负载均衡？
* 面对秒杀等高并发场景，系统有哪些限流、降级或熔断的应急手段？

## 5. 监控与运维基础设施

* 系统是否接入了日志集中管理工具（如 ELK、Graylog）？
* 系统是否有 APM 性能监控工具（如 SkyWalking、Pinpoint、或者是早期的 New Relic、OneAPM）？
* 服务器的基础监控（CPU、内存、磁盘、带宽）接入的是什么系统（如 Zabbix、Prometheus+Grafana）？
* 当系统发生严重错误（如 PHP Fatal Error 或数据库连接失败）时，是否有自动化报警机制（邮件、钉钉、企业微信）？
* 系统的 SSL 证书（HTTPS）是在哪里配置的（Nginx、网关，还是云厂商负载均衡器）？
* 是否有第三方外部监控（如听云、监控宝）在定时拨测网站可用性？

## 三、 应用架构 (Application Architecture)
核心目标：摸清代码的组织形式、模块边界和子系统划分。
## 1. 系统拆分与模块设计

* 整个电商系统由哪几个独立的应用子系统组成（如前台商城、商家后台、总管理后台、WMS、ERP）？
* 前台商城是前后端分离的（如 Vue/React + API），还是传统的 MVC 模板渲染（如 Smarty、PHP 刀片模板）？
* 前后台应用是部署在同一个代码仓库里，还是拆分成了多个代码仓库？
* 系统是如何进行模块化划分的（如核心的 Order、Product、User 模块是否独立）？
* 系统是否存在 H5 移动端、小程序、App，它们是共用一套 API 还是各自独立？
* 系统的后台管理系统（Admin）使用的是什么前端框架（如易于老系统的 Bootstrap、Layui、AdminLTE）？

## 2. 代码分层与复用

* 代码在框架层面上是如何分层的（除了经典的 Controller、Model、View，是否有 Service 层、Repository 层、Logic 层）？
* 复杂的电商业务逻辑（如复杂的下单计算）是写在 Controller、Model 还是专门的 Service 里？
* 多个应用子系统（如前台和后台）之间如何复用底层的公共业务逻辑？
* 系统中有没有使用到设计模式（如工厂模式、单例模式、策略模式），主要应用在什么地方（如支付、物流网关适配）？
* 公共类库和辅助函数（Helpers）是如何组织和全局加载的？
* 系统是否使用了早期遗留的外部大插件/扩展包（例如 PHPExcel、TCPDF），它们放在什么目录？

## 3. 接口与服务通信

* 前后端交互或三方对接的 API 接口采用的是什么协议（RESTful JSON、XML、RPC、还是 SOAP）？
* 接口的统一返回格式（Wrapper）是怎样的（包含哪些状态码和错误字段）？
* 不同子系统之间如果需要同步调用，是通过 HTTP 接口还是通过内部 RPC 通信？
* 接口的身份认证（Auth）采用的是什么方案（Session、Cookie、Token 还是 JWT）？
* 接口的版本控制（Versioning）是如何实现的（如 /api/v1/ 还是通过请求头控制）？
* 系统如何处理接口请求的幂等性（防止前端重复点击造成重复下单/重复支付）？

## 4. 第三方服务集成

* 短信服务集成了哪家厂商（如阿里云通信、腾讯云短信、网易云信）？
* 实名认证、身份证识别、图形验证码等集成了什么第三方服务？
* 系统是否对接了第三方的 ERP、WMS 或者是外部仓储系统（如菜鸟、京东仓）？
* 系统是否集成了第三方数据分析或埋点 SDK（如百度统计、友盟、神策数据）？
* 客服系统是自研的，还是集成了外部服务（如美洽、智齿客服）？
* 电子发票功能对接的是哪家税控平台（如航天信息、百望云）？

## 四、 数据架构 (Data Architecture)
核心目标：理清数据的存储结构、表关系、生命周期及流转。
## 1. 数据库表设计

* 核心业务表（用户表、商品表、订单表、支付流水表）的表结构和主外键关系是怎样的？
* 系统中大概有多少张业务表？是否有长期废弃但未删除的死表？
* 表名和字段名的命名规范是什么（驼峰式、下划线、还是拼音简写）？
* 核心业务表的索引建立情况如何？是否存在大量无用索引或缺失关键索引？
* 系统是如何设计商品多属性（SKU）的数据库模型的（是 EAV 模型、动态宽表，还是 JSON 字符串字段）？
* 订单历史快照数据（如购买时的价格、商品标题、图片）是如何在订单详情表中冗余存储的？

## 2. 状态机制与流水记录

* 订单状态字段、支付状态字段、物流状态字段分别是哪些，各自的数字枚举值代表什么含义？
* 系统是否存在一张专门的订单状态变迁日志表（用于追溯是谁在什么时候把订单改成什么状态）？
* 资金/余额变动是否有严密的流水账（Wallet Log / Balance Log）记录？
* 积分变动、优惠券核销是否有不可逆的日志表支持？
* 库存扣减和回滚是否有明细日志（Inventory Log），以便在库存对不上时进行对账？
* 用户关键操作（如修改密码、提现、管理员修改商品价格）是否有操作审计日志？

## 3. 缓存设计与一致性

* 哪些高频访问的数据放入了缓存（如商品详情、分类树、系统全局配置）？
* 缓存的过期时间（TTL）策略是怎样的？是否存在全网缓存同时失效（缓存雪崩）的隐患？
* 数据更新时，缓存的同步策略是什么（是先更新数据库再删缓存，还是直接让缓存超时过期）？
* 系统有没有做防止缓存穿透（查询不存在的数据导致直接打到 MySQL）的保护机制？
* 系统中的大 Key（如极大的数组或对象）是如何存储和处理的？
* 分布式锁（如果是 Redis 实现）在系统哪些高并发写场景中被使用了？

## 4. 数据生命周期与归档

* 历史老订单、历史日志表（如 3 年前的订单、亿级的用户访问日志）是否有定时归档或清理策略？
* 历史数据被移到了哪里（归档库、冷存储，还是直接通过脚本 Delete 掉）？
* 数据库的自增 ID 是否面临溢出风险（例如某些大流量日志表的 ID 类型是否为 INT 而非 BIGINT）？
* 图片、音视频等静态文件的生命周期是如何管理的（是否存在大量商品删除了但图片依然占用服务器磁盘的情况）？
* 系统中的敏感用户数据（如身份证号、银行卡号、密码）在数据库中是如何加密存储的？
* 是否使用了数据仓库、数据湖或大数据分析工具（如 ClickHouse）来做报表查询？

## 五、 安全架构 (Security Architecture)
核心目标：PHP 5.6 极易受到攻击，必须找出系统的漏洞、防御机制与权限漏洞。
## 1. PHP 5.6 特定安全隐患

* 由于 PHP 5.6 早已停止官方维护，当前运行的 PHP 版本是否存在尚未修复的已知 CVE 高危漏洞？
* 系统代码中是否存在使用 unserialize() 函数处理用户可控输入的风险（反序列化漏洞）？
* 代码中是否还在使用已被废弃且极不安全的 mysql_* 系列函数（而非 PDO 或 mysqli）？
* PHP 配置文件 php.ini 中是否关闭了高危配置（如 allow_url_include = Off, expose_php = Off, display_errors = Off）？
* 代码中是否调用了 eval(), exec(), system(), passthru() 等高危系统执行函数？
* 是否有防止 PHP 报错泄漏服务器绝对路径、代码逻辑等敏感信息的全局异常捕获机制？

## 2. 常见 Web 攻击防御

* 系统如何防御 SQL 注入（代码中是否严格使用了预编译语句 PDO 来绑定参数，还是大量使用字符串拼接）？
* 系统如何防御 XSS（跨站脚本攻击）？在前端/后端渲染或接收富文本（如商品详情、用户评价）时是否有严格的过滤（如使用 HTMLPurifier）？
* 核心的写操作接口（如转账、下单、修改密码）是否设计了有效的 CSRF（跨站请求伪造）令牌防御机制？
* 文件上传功能（如用户头像、商户资质）是否有严格的文件类型、后缀名校验以及防止执行（禁止上传 .php 后缀）的机制？
* 系统是否有文件包含防御，是否存在 include($_GET['page']) 这种高危代码？
* 针对暴力破解（如刷登录、刷短信验证码），系统是否有图形验证码、极验、请求频率限制（Rate Limiting）等机制？

## 3. 业务逻辑与权限安全

* 系统的后台管理（Admin）权限控制使用的是什么模型（如传统的 RBAC、基于节点的权限表，还是硬编码控制）？
* 系统是否存在越权漏洞（水平越权：用户 A 通过修改订单 ID 越权查看用户 B 的订单；垂直越权：普通用户猜到后台 URL 即可直接访问）？
* 在秒杀、优惠券领取等高价值业务中，如何防止黄牛刷单、薅羊毛（是否有设备指纹、风控检测或账号防刷逻辑）？
* 高价值的资金操作（如提现、余额转账）是否需要二次输入支付密码或手机验证码？
* 前后端计算订单总价时，是否存在安全校验漏洞（例如用户在前端通过 F12 修改商品单价为 0.01 元，后端是否会直接信任并创建订单）？
* 优惠券的扣减值是否有可能在极速并发下变成负数，从而导致“越买余额越多”的逻辑漏洞？

## 4. 数据与传输安全

* 全站是否都强制走 HTTPS 协议？是否存在部分老的支付回调接口还在使用不安全的 HTTP 协议？
* 用户的登录密码采用的是什么加密算法（如古老的 md5($password)、md5(md5+salt) 还是更安全的 password_hash()）？
* 对外的 API 接口是否设计了签名校验机制（如通过 AppSecret 计算 sign）来防止请求被中间人篡改？
* 敏感数据（如商家结算银行卡号、手机号、身份证号）是否在数据库中明文存储？前台展示时是否有脱敏处理（如 138****8888）？
* 系统的数据库连接配置、三方支付密钥（如微信支付商户私钥）是否明文硬编码在代码文件中？
* 系统的敏感操作、权限变更是否有完整的、无法被篡改的审计日志记录？

## 六、 开发架构 (Development Architecture)
核心目标：弄清平时怎么协作、代码怎么管理、新功能怎么上线。
## 1. 版本控制与团队协作

* 代码使用什么版本控制工具（Git 还是老旧的 SVN）？
* Git 的分支管理策略（Git Flow）是怎样的（有哪些固定分支，如 master, develop, test）？
* 平时开发新需求、修复 Bug 的流程是怎样的（是直接在主分支提交，还是走 Pull Request/Merge Request 评审）？
* 目前团队中还有多少人在共同维护这个系统？各自负责哪些模块？
* 历史的代码提交记录（Commit Message）是否有统一的规范要求？
* 是否有相关的业务文档、架构图、数据字典或接口文档（如 Swagger、Apifox），它们保存在哪里？

## 2. 依赖管理与扩展

* PHP 依赖项是通过 Composer 进行管理的，还是把第三方库直接打包放进了代码目录（如 vendor/, libs/）？
* 系统依赖了哪些非标准的 PHP 扩展（如 redis, swoole, gd, mcrypt, curl, mbstring），它们的版本要求是什么？
* 系统是否引用了前端的 npm/yarn 依赖包？在前端是如何编译、打包和发布的？
* 如果使用的是很老的框架，是否有私有或闭源的依赖组件无法通过公开渠道下载？
* 修改系统公共依赖库时，需要执行哪些回归测试流程以确保不破坏历史老功能？
* 如何处理团队开发成员本地环境与线上生产环境 PHP 扩展不一致的问题？

## 3. 环境与配置管理

* 系统分为几个日常环境（如本地开发环境 Local、测试环境 Test、预发环境 Staging、生产环境 Production）？
* 不同环境之间的配置文件（如数据库连接、三方密钥、应用开关）是如何隔离和管理的（是通过 .env 文件、特定的配置目录，还是硬编码切换）？
* 本地开发环境是如何搭建的（使用的是 Docker、集成环境如 XAMPP/phpStudy，还是全手动配置）？
* 测试环境的数据是从哪里来的（是手工造数据、自动脚本生成，还是直接从线上脱敏导入）？
* 当线上数据库结构发生变更（加字段、改索引）时，开发团队如何进行同步和演进（使用 Migrations 脚本，还是手工人工执行 SQL）？
* 本地开发时如果需要调试微信支付回调、短信回调等外部通知，是如何做内网穿透的？

## 4. 测试与代码质量

* 这个老系统是否有自动化单元测试（如 PHPUnit）或集成测试？如果有，目前的测试覆盖率大概是多少？
* 平时测试新功能主要是靠自动化测试还是全人工点点点（手工黑盒测试）？
* 是否有静态代码检查工具（如 PHPCodeSniffer、PHPStan）在规范代码风格和排查低级语法错误？
* 系统里是否存在严重的“代码坏味道”（如几千行的超长文件、满屏的 if-else 嵌套、大量重复复制的代码），如何识别它们？
* 系统上线前是否有常规的压测流程（如使用 JMeter、ApacheBench 进行压测）？
* 研发团队如何定义和处理线上突发的 Bug（是否有 Bug 追踪系统，如 Jira、禅道、Redmine）？

## 七、 运行架构 (Runtime Architecture)
核心目标：了解系统在服务器上怎么活着的，挂了怎么救，怎么扩容。
## 1. 服务器硬件与拓扑

* 系统运行在什么操作系统上（如 CentOS 6/7、Ubuntu、Windows Server）？具体的操作系统内核版本是多少？
* 线上生产环境一共有多少台服务器？它们各自的硬件配置（CPU、内存、磁盘、带宽）是怎样的？
* 整个系统的线上拓扑图是怎样的（流量进入网关后，如何流转到 Web 服务器、缓存服务器和数据库服务器）？
* 服务器是托管在自建机房，还是运行在云厂商（如阿里云、腾讯云、华为云、AWS）的虚拟机（ECS/CVM）上？
* 生产环境的服务器之间网络是如何互通的（是否在同一个 VPC 内，是否有严格的安全组/防火墙隔离）？
* 在不同的服务器之间，PHP 的 Session 是如何保持一致和共享的（例如通过 Redis 共享，还是做了 IP 粘性 Hash 负载均衡）？

## 2. 部署与自动化运维

* 代码是如何发布到线上生产环境的（是通过手动 FTP/SCP 覆盖、通过 Jenkins/GitLab CI 自动化部署，还是写了自研的 Shell 脚本）？
* 发布新版代码时是否需要停机维护（挂维护公告），还是可以做到完全无缝的滚动发布（Zero-downtime Deployment）？
* 如果在发布后发现重大 Bug，系统如何进行快速回滚（有没有一键回滚到上一个稳定版本的机制）？
* Web 服务器（Nginx/Apache）的静态资源根目录和 PHP 文件的权限是如何划分的（是否做到了 Web 用户只读，防范木马写入）？
* 代码发布后，PHP 的 Opcache 缓存是如何清理的（如果不清理可能会导致新代码不生效）？
* 系统部署过程中涉及的日志目录（如 runtime/, logs/）是否具有正确的写权限，是否配置了定时按天切分与清理？

## 3. 备份、容灾与高可用

* 生产环境数据库（MySQL）的备份策略是怎样的（是每天全量冷备、实时热备、还是开启了 Binlog 增量备份）？
* 备份文件保存在哪里？是否有定期做过备份文件的恢复演练，确保备份真的可用？
* Redis 缓存的数据是否有持久化策略（AOF 还是 RDB）？如果 Redis 突然挂掉重启，数据会丢失吗？
* 系统是否有异地容灾、同城双活或者多机房备份的机制（还是说所有鸡蛋都在单机/单机房这一个篮子里）？
* 如果核心的云厂商突然发生大面积网络故障，团队是否有应急预案？
* 如果主数据库挂了，从库切主库（Failover）是自动完成的（如 MHA、Orchestrator），还是需要运维人工去改配置切流量？

## 4. 扩容与性能瓶颈

* 当面临双11、大促等大流量业务时，系统如何进行水平扩容（加 Web 服务器方便吗，数据库和缓存是否会成为最终的瓶颈）？
* 目前系统的整体硬件资源利用率日常是多少（CPU、内存、磁盘 I/O 长期处于什么水平）？
* 系统当前最消耗性能的“性能瓶颈点”在哪里（是复杂的 SQL 查询、频繁的三方网络 I/O、还是 PHP 自身的密集计算）？
* 系统是否开启了 PHP Opcache 扩展？相关的缓存大小（opcache.memory_consumption）是否配置充足？
* 服务器的外部网络带宽是否有限流或突发带宽上限？大流量下会不会因为带宽跑满而导致网站瘫痪？
* 线上服务器的磁盘空间增长速度如何？是否会因为日志或上传文件暴增而导致磁盘在短时间内被塞满？
