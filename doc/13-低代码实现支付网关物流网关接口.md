基于 **Spring Cloud Alibaba** 与 **Vue 3** 的架构，要通过“低代码”方式实现“统一支付接口”和“统一物流接口”，核心逻辑在于**“SPI (Service Provider Interface) 策略模式 + 动态规则引擎/数据驱动”**。

通过将不同的支付渠道（支付宝、微信、银联、PayPal）和物流渠道（顺丰、中通、菜鸟、快递100）抽象为**标准元数据与统一接口**，前端通过可视化表单拖拽配置，后端通过动态编译或动态路由执行，即可达成低代码甚至零代码接入新渠道的目的。

## 二、 后端低代码架构实现 (Spring Cloud Alibaba)

## 1. 统一支付微服务 (Plugin-SPI 架构)

为了实现低代码接入，后端不硬编码支付平台，而是定义统一的输入输出实体。

- **统一聚合支付接口定义：**

```java
public interface UnifiedPayPlatform {
    // 统一发起支付（支持 H5, APP, 扫码, 小程序）
    PayResponse pay(PayRequest request);
    // 统一退款
    RefundResponse refund(RefundRequest request);
    // 统一查询
    QueryResponse query(String orderNo);
    // 统一关闭订单
    Boolean close(String orderNo);
}
```

- **低代码动态加载机制：**
  利用 **Nacos** 作为配置中心。当需要增加或修改支付参数（如商户号、私钥）时，直接在前端低代码页面修改，保存后推送到 Nacos，通过 `@RefreshScope` 动态更新映射表，无需重启微服务。

```java
@Component
@RefreshScope
public class PayChannelFactory {
    // 内存中缓存渠道实例：ChannelCode -> ChannelInstance
    private final Map<String, UnifiedPayPlatform> channelMap = new ConcurrentHashMap<>();

    @NacosValue(value = "${pay.channels.config}", autoRefreshed = true)
    private String channelsJson;

    // 监听配置变化，动态构建或更新支付实例（反射/容器注入）
    @PostConstruct
    public void initChannels() {
        // 解析 channelsJson，低代码配置哪些渠道，这里就动态初始化对应的 Bean
    }

    public UnifiedPayPlatform getChannel(String channelCode) {
        return channelMap.get(channelCode);
    }
}
```

## 2. 统一物流微服务 (元数据驱动)

针对物流，不仅是下单发货，最核心的是**轨迹格式的统一**。

- **统一轨迹标准模型 (DTO)：**

```java
public class LogisticsTraceDTO {
    private String trackingNo;      // 物流单号
    private String carrierCode;     // 承运商编码 (SF, ZTO)
    private String status;          // 统一状态：WAIT_PICK(待揽收), SHIPPING(运输中), DELIVERING(派送中), SIGNED(已签收)
    private List<TraceNode> traces; // 节点详情
}

public class TraceNode {
    private LocalDateTime dateTime; // 时间
    private String content;         // 描述
    private String location;        // 当前网点/城市
}
```

- 解耦回调与轮询：
  - **顺丰/菜鸟等（支持 Webhook）：** 提供统一的 `/api/logistics/callback/{carrierCode}` 接收端，采用**策略模式**分发解析。
  - **中小快递（不支持 Webhook）：** 引入 **Quartz/Xxl-job** 定时任务，低代码平台配置“轮询策略（如：未签收订单每 2 小时查一次）”，动态触发查询。

## 四、 核心闭环：全链路状态机与分布式一致性

支付与物流天然涉及长周期、跨系统的状态变更。为保证低代码框架的高可靠性，需要处理好两件事：

## 1. 状态机管理订单生命周期

利用状态机规范订单状态。严禁人工随意编写 `update status = xxx`。

- **订单状态机：** `INIT (创建)` -> `WAIT_PAY (待支付)` -> `PAID (已支付)` -> `SHIPPED (已发货)` -> `RECEIVED (已收货)`。
- **物流状态机：** `WAIT_PICK (待揽收)` -> `TRANSIT (运输中)` -> `SIGNED (已签收)`。
- 状态的推进必须通过统一的消息中心或事件驱动（如使用 `Spring Cloud Stream` 绑定 RocketMQ/RabbitMQ）来通知订单中心进行联动修改。

## 2. 分布式事务与高并发防护

- **Seata 柔性事务 (Saga 模式)：** 下单并调用物流预下单、或者扣减库存时，由于是跨微服务调用，采用 Seata 确保数据的最终一致性，防止“付了钱系统没改状态”或“物流单生成了订单却失败”的情况。
- **Sentinel 防护：** 三方支付回调和物流轨迹查询接口极其容易受到外部攻击或瞬时高并发，必须在服务网关层利用 **Sentinel** 配置针对 `/api/pay/callback/*` 的热点参数限流与防刷。

## 一、 国内主流支付渠道接口（支付宝、微信支付）
国内支付接口高度依赖场景化（Web/App/小程序）以及异步回调（Webhook）机制。
## 1. 支付流（核心交易发起）

* APP 支付接口：返回签名后的字符串，供手机原生 APP 拉起支付宝/微信客户端。
* H5/手机网站支付接口：返回一个支付跳转 URL，用于手机浏览器或微信外的 H5 页面。
* 电脑网站/Native 支付接口：返回一个用于生成二维码的链接（URL），用户用手机扫码支付。
* JSAPI/小程序支付接口：返回一串 JSON 配置参数，供微信/支付宝内嵌的小程序或公众号直接调用内置 JS 桥接器付款。
* 付款码/当面付接口：商户用扫码枪读取用户手机上的付款码，直接扣款（B扫C）。

## 2. 交易后续与状态同步

* 主动查询接口：由于网络可能波动，商户后端用于主动向支付平台查询订单的真实支付状态。
* 关闭订单接口：订单超时未支付时，商户主动调用以释放商品库存、防止用户继续付款。
* 异步通知接收（Webhook）：支付成功后，支付平台服务器向商户服务器发送的 POST 回调请求。商户必须以此通知作为发货的最终依据。

## 3. 退款与资金流

* 申请退款接口：支持全额或部分退款，需传入原交易号和退款单号。
* 退款查询接口：由于退款通常是异步落账，用于查询退款是否真正到账。
* 下载对账单接口：每日定时调用，获取前一天的资金流水账单（CSV格式），用于财务系统自动对账。

## 二、 国外主流支付渠道接口（Stripe、PayPal、Adyen）
国外支付（尤其是 Stripe）近年来全面转向以“支付意图（Payment Intent）”为核心的状态机模式，且极度看重 PCI-DSS 安全合规（避免商户后端直接接触信用卡号）。
## 1. 核心交易流（以 Stripe / Adyen 信用卡为主）

* 创建支付意图接口（Create PaymentIntent）：商户后端发起，告诉支付平台“这笔订单要付多少钱、什么币种”，平台返回一个加密的 Client Secret。
* 确认支付接口（Confirm PaymentIntent）：前端利用官方组件（如 Stripe Elements）收集卡号并绑定 Client Secret 直接提交给支付平台。商户后端不触碰敏感卡号。
* 3D 认证接口（3D Secure / SetupIntent）：触发欧洲强客户认证（SCA）时，拉起银行验证码/指纹页面，确认后才推进支付状态。

## 2. PayPal 专属交易流（钱包/快捷支付）

* 创建订单接口（Create Order）：商户调用后，返回一个 PayPal 的登录跳转链接。
* 捕获订单接口（Capture Order）：用户在 PayPal 页面登录并同意付款后，跳转回商户网站，商户后端必须调用此接口才能真正把钱从用户账户扣除。

## 3. 跨境与循环扣款

* 客户管理接口（Customers API）：用于在国外支付平台保存用户的支付凭证（如绑定的信用卡 Token）。
* 订阅/免密代扣接口（Subscriptions API）：针对 SaaS 服务或定期订购业务，由平台定时自动触发扣款，无需用户每次确认。
* Webhooks 异步事件接收：国外渠道把所有状态变更都视为事件（如 payment_intent.succeeded），商户必须挂载统一的 Webhook 接收端。

## 三、 统一低代码平台中，接口如何抽象？
在低代码系统的“统一支付接口”中，你需要把上述所有渠道的个性化接口，强制合并为以下 5 个标准的统一 HTTP API/SPI 方法：

| 标准抽象接口                | 作用说明         | 映射的底层渠道接口示例                                       |
| --------------------------- | ---------------- | ------------------------------------------------------------ |
| /api/pay/unified/create     | 统一创建交易     | 微信 JSAPI / 支付宝 H5 / Stripe PaymentIntent / PayPal Create Order |
| /api/pay/unified/query      | 统一订单查询     | 微信订单查询 / 支付宝当面付查询 / Stripe Retrieve Intent     |
| /api/pay/unified/refund     | 统一发起退款     | 微信退款 API / 支付宝退款 API / PayPal Refund                |
| /api/pay/unified/close      | 统一关单/撤销    | 微信关单 / 支付宝撤销 / PayPal Void Order                    |
| /api/pay/callback/{channel} | 统一异步回调网关 | 接收各渠道 Webhook 并由策略模式路由分发                      |
