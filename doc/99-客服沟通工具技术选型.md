## 客服沟通工具技术选型

客服沟通工具过去经历过使用

- CIM
- Box‑IM

## 一，CIM

CIM (Cross‑IM) 是一款基于 Netty 开发的 Java 开源分布式即时通讯内核，底层基于 SpringBoot2，采用 Protobuf 做消息编解码，同时支持 TCP 二进制自定义协议与 WebSocket 双接入，支持私有化部署，适合 APP、Web 端消息推送与即时聊天场景。

单机部署时所有能力集成在`cim‑server`服务中，无需额外路由组件；集群模式可启用独立路由服务，依赖 Zookeeper 完成 IM‑server 节点注册发现，Redis 存储在线状态、客户端路由信息，MySQL 持久化会话与离线消息Gitee。内置心跳保活、断线自动重连、离线消息、消息加密、APNs 苹果推送等能力，支持私聊、群聊，可水平扩展支撑大量长连接。该项目聚焦 IM 底层通信，**不提供客服坐席、会话排队等业务逻辑**，无开箱即用 Vue Web 前端，聊天界面需要自行开发或对接第三方 UI 组件。项目实战成熟，但基础版本为 SpringBoot2，迁移至 SpringBoot3 需要处理 javax/jakarta 包、Hibernate 版本的大量兼容改造；集群环境需要运维 Zookeeper，会提升中间件运维成本。

## 二，Box‑IM

Box‑IM‑SpringBoot3 是面向 Web 优先场景的开源 IM 内核，原生基于 SpringBoot3、JDK17 构建，底层采用 Netty，以 WebSocket 作为主要接入协议，支持 JSON/Protobuf 消息编解码。架构分为业务平台服务`im‑platform`与长连接服务`im‑server`，集群仅依赖 Redis 实现跨节点消息转发，无需 Zookeeper，容器 K8s 部署友好。支持私聊、群聊、已读回执、图片文件语音、多端同步、离线消息，集成 MinIO 做富媒体存储，附带可复用的 Vue3 Web 聊天前端示例。项目同样只提供 IM 底层能力，不内置客服坐席、会话分配排队业务，上层客服业务需要自主开发；缺少原生 TCP 二进制协议与 APNs 推送，该部分需要自行扩展，社区活跃度较好，文档与 Demo 相对完善。

## 三，总结结论

| 对比维度           | CIM（cross‑im）                                              | Box‑IM‑SpringBoot3（盒子IM）                                 |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **SpringBoot版本** | 2.x，**需要改造升级到SpringBoot3（javax→jakarta）**          | **原生SpringBoot3，JDK17+开箱即用**，无需大改包名            |
| **底层通信**       | Netty；同时支持 **TCP自定义二进制协议 + WebSocket**；protobuf编解码 | Netty；**主要面向WebSocket**；JSON/protobuf；Web优先场景友好 |
| **集群架构**       | 多服务组件：cim‑forward‑route(路由) + cim‑server(长连接服务)；**依赖Zookeeper做服务注册发现**；Redis存储路由状态 | im‑platform(业务http) + im‑server(长连接ws)；**仅依赖Redis做跨节点消息转发，不需要Zookeeper**；K8s友好 |
| **消息跨节点**     | Zk+Redis协同，组件多运维重                                   | Redis List队列实现跨im‑server消息投递，组件少，部署简单      |
| **存储**           | MySQL(JPA)+Redis；离线消息、会话存储                         | MySQL+Redis+MinIO(文件图片存储)；完整聊天记录持久化，文件能力完善 |
| **前端现状**       | **无完整Web/Vue3前端**；需要自己全部写聊天UI（你要对接Chotto‑UI等组件） | 自带Vue Web前端、Uniapp；可直接参考聊天页面实现逻辑，可裁剪复用组件代码 |
| **内置能力**       | 私聊、群聊、离线消息、心跳保活、断线重连、消息加密、APNs推送（你的配置中已看到apns模块）；**没有坐席/会话排队客服业务** | 私聊、群聊、已读回执、图片/文件/语音、WebRTC音视频、多端同步；**同样没有客服坐席排队分配业务** |
| **协议端口**       | 自定义TCP端口（23456）+WebSocket端口（34567），两套端口需要开放防火墙 | 主要WebSocket；http业务端口+ws端口，运维简单                 |
| **依赖中间件**     | MySQL、Redis、**Zookeeper**（强依赖集群）                    | MySQL、Redis，可选MinIO；**无Zookeeper依赖**                 |
| **维护更新**       | 项目较早，社区活跃度一般，issue响应慢                        | 社区活跃，SpringBoot3分支持续迭代，demo可在线体验            |
| **部署复杂度**     | 高，多组件，Zk运维成本不可忽略                               | 中等，两个核心服务platform+im‑server；docker支持好，适合k8s  |

## CIM 优缺点分析
### ✅优点
1. **协议能力很强**：同时支持TCP二进制+WebSocket；适合APP、小程序、网页多端接入；protobuf二进制协议，带宽占用低，弱网表现好。
2. 已经内置APNs苹果推送模块，移动端推送不用从零开发，你手上配置已经包含apns配置。
3. 底层IM内核经过多年项目实战，长连接、心跳、断线重连、离线消息逻辑成熟。
4. 消息加密、自定义协议扩展能力强，适合物联网、APP推送场景。

### ❌缺点（选型最大痛点）
1. **原生SpringBoot2，迁移SpringBoot3成本高**：大量javax包需要改成jakarta；JPA(Hibernate5→6)大量兼容坑，这是最大工作量。
3. **没有Web/Vue前端实现**，聊天UI全部从零对接第三方组件（Chotto‑UI），需要自己封装ws/tcp客户端。
4. 模块拆分多：route路由服务 + im‑server长连接服务，至少2个服务，部署运维负担高。
5. 社区活跃度一般，文档偏向底层内核，业务层示例较少。
6. **同样只是IM内核，没有客服坐席、访客分配、会话排队逻辑，上层业务全部自己写**。

> CIM适合：APP为主，同时有TCP长连接需求，团队愿意承担SpringBoot2升级3和。

## Box‑IM‑SpringBoot3 优缺点
### ✅优点
1. **原生SpringBoot3 + JDK17**，和你的技术栈完全对齐，**不需要做javax/jakarta迁移改造**，拿来即可二次开发。
2. **不需要Zookeeper，仅靠Redis完成集群跨节点消息转发**，中间件少，运维压力小，非常适合K8s容器部署。
3. 自带Vue Web聊天前端代码，可以直接复用UI逻辑，或者抽取组件对接你的业务，减少前端开发量。
4. 能力完整：图片、文件、语音、已读未读、WebRTC音视频、多端同时在线同步，离线消息处理完善，MinIO集成开箱即用做文件存储。
5. 架构拆分清晰：im‑platform处理业务http接口；im‑server专注WebSocket长连接推送；模块职责清晰。
6. 社区活跃，在线demo可以直接体验，文档相对完善。

### ❌缺点
1. **以WebSocket为主要接入方式，没有成熟TCP二进制协议支持**；如果你需要APP原生TCP长连接，需要自己扩展开发。
2. **依然是IM内核，不是成品客服系统**，坐席管理、访客接入、会话排队、会话关闭、满意度等业务全部需要自己开发。
3. WebRTC音视频依赖SSL证书，内网环境调试会有额外成本。
4. 没有内置APNs推送，苹果离线推送需要自己扩展开发。
